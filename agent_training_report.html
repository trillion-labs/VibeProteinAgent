Section 1

Executive summary and reading guide

The dominant story in modern agent research is that the model has stopped being the bottleneck. Quality is now decided by the harness around it — the tool contracts, the state it sees, the feedback it gets, and the verifier that decides whether an answer is good. For a small team like VibeProteinAgent, that is good news, because the cheapest interventions are also the highest-leverage.

Main conclusion

The highest-return path is not large-scale reinforcement learning. It is a disciplined agent harness that logs every attempt, validates tool plans before execution, turns tool failures into structured repair tasks, and trains small models only after enough verified trajectories exist. Until the harness produces clean, replayable data, training will only encode whatever noise the harness already had.

Recommendation

Treat the framework itself as the learning system. Use the strongest available planner online, collect every trace it produces, filter those traces with deterministic scientific verifiers, and only then distill the winning traces into cheaper planners, preference models, and small task-specific verifiers. Each stage produces an artifact the next stage needs.

This conclusion is consistent across the lines of work surveyed in this report: ReAct, Toolformer, Reflexion, Tree of Thoughts, LATS, Voyager, ToolLLM, AgentTuning, AgentGym, WebArena, SWE-bench, Tool-MVR, and the 2025–2026 wave of process-supervision and verifier-guided training papers. The detail differs, but the underlying claim is the same: agent quality depends less on raw language generation and far more on the interface between model, state, tools, feedback, and evaluation. The model needs a narrow action language, reliable observations, budget-aware search, and feedback that can tell us not only whether a workflow ended successfully but which step helped or hurt.

For protein design and scientific workflows, this lesson is amplified rather than softened. A protein agent can produce fluent hypotheses while still being wrong about sequence–function causality, structure confidence, binding energetics, or wet-lab feasibility. Pretty prose is not evidence. The framework therefore has to separate language reasoning from executable scientific evidence, persist provenance for every artifact, and require explicit validation gates before claiming a candidate is ready to submit.

How to read this report

The report is ordered so that each section produces what the next section consumes. Section 2 establishes the general-domain lessons that shape every design decision later. Section 3 turns those lessons into a concrete architecture, with reliability mechanisms that VibeProteinAgent can adopt or already has. Section 4 explains the staged training recipe and exactly which traces and labels are worth collecting. Section 5 maps everything onto the protein domain, where the literature is younger and the failure modes are more dangerous. Section 6 grounds the discussion in the current code. Section 7 ends with a roadmap and a decision matrix for what to implement first.

VPA takeaway

The order matters: harness → data → small SFT → preferences → verifiers, not the other way around. Any training investment before the harness reliably produces clean trajectories will entrench whatever bugs the harness currently has, including invalid tool calls and shallow successes that look like wins on a dashboard.

Section 2

General LLM agent foundations

General-domain agent research has moved through three overlapping waves, and each wave left behind one durable lesson. We start here because every architectural and training decision later in the report leans on one of these lessons, and because protein-domain agents are still climbing the same curve that general-domain agents climbed three years ago.

The three waves of agent research, in one paragraph each

Wave 1 — prompting patterns. The earliest work (ReAct, Tree of Thoughts, Reflexion) showed that interleaving reasoning with action, branching over candidate thoughts, and feeding verbal self-criticism back into context can lift task performance without any new training. The durable lesson is that exposing intermediate reasoning to the environment — and the environment back to the reasoning — is more important than the specific prompt template used. Frameworks that hide tool failures behind prose summaries throw away exactly the feedback the model needs to recover.

Wave 2 — tool learning at scale. Work such as Toolformer, ToolLLM, Voyager, and AgentTuning turned tool use itself into a learnable behavior, either through self-supervised filtering (Toolformer), curated trajectory mixtures (AgentTuning), or accumulated skill libraries (Voyager). The durable lesson is that tool-use data, not generic instruction data, is what teaches an agent to be reliable, and that hallucinated tool calls are the single most common quality failure. Synthetic trajectories must be validated against the real tool catalog before they enter any training set.

Wave 3 — verifiers, process supervision, and budgeted search. The current wave (LATS, AgentGym, Tool-MVR, Self-Verification Sampling, RAGEN, SPA-RL, Automated Process Supervision) is about giving the agent or its trainer fine-grained signal about which step in a long trajectory was right or wrong, instead of only an end-of-episode reward. The durable lesson is that verifiers operating on intermediate state are cheaper, more sample-efficient, and more transferable than monolithic preference models that only see the final answer.

Paper-to-lesson mapping

The table below converts each line of work into a single concrete framework lesson for VibeProteinAgent. It is meant to be read as the practical compression of the three waves above: each row exists because at least one well-known paper made the same mistake first and showed how to avoid it.

ReAct Interleaving reasoning and actions helps agents update plans from observations and recover from exceptions. Voyager A skill library plus environment feedback lets an agent accumulate reusable behaviors over time. What the 2025–2026 wave adds: process supervision is cheap when state is structured

The newest agent-training papers sharpen the budget lesson directly. RAGEN reports that multi-turn agent RL collapses into shallow strategies when rewards are sparse and end-of-episode only, even with sophisticated optimizers. SPA-RL and RRO both respond by attributing credit to individual steps, either through stepwise progress decomposition or rising-reward trajectory selection. SWE-Gym shows that the same executable environment can train both the agent and its verifier from the same trajectory pool, which is the practical cost-saver behind much of modern coding-agent work. Automated Process Supervision closes the loop by generating step-level rewards without expensive human annotation.

The translation to VibeProteinAgent is direct. Deterministic workflow state — schema validation, completed jobs, domain QC, artifact provenance — is already an automatic process-supervision signal sitting unused in the workspace. The team does not need to label rewards manually for most training data; they need to expose the signals the workspace already produces and route them into a structured trace store.

VPA takeaway

VPA already has the substrate that papers like SWE-Gym treat as a key advantage: a deterministic execution environment with persisted state, jobs, artifacts, and retries. The work is not to invent process supervision from scratch but to surface and label the signals the workspace already emits, then design the planner so that each step exposes a check the verifier can score.

Section 3

Practical agent architecture

Product-grade agents are compound systems, not single models. The codebases that ship reliable autonomy — OpenCode, Codex CLI, Claude Code, LangGraph, MCP-based ecosystems — all converge on the same blueprint: a planner loop surrounded by state management, permissions, typed tool schemas, durable logs, context packing, retries, and verification. The job of this section is to extract from those systems the reliability mechanisms that VibeProteinAgent should adopt or already has.

High-level agent architecture

The diagram below is the reference architecture this report assumes. Read it left-to-right, top-to-bottom. The top row is the synchronous request path: the user goal enters the planner, which proposes a workflow that is then compiled and validated locally before any approval gate fires. The middle row is the execution substrate: a tool registry, a job execution layer, and a verifier that decides whether the run is complete or has to be repaired. The bottom row is persistence: every step is written to durable state, and the same state stream feeds the training dataset. Arrows that loop back upward — verifier to planner, training set to planner — are the feedback paths that turn one good run into improvement on the next.

The tool-use and verification loop, zoomed in

The architecture diagram makes the outer system shape clear, but the inner loop is where most agents fail. The diagram below isolates a single round of action. The planner emits a structured tool call; the compiler validates the call against the schema before it ever reaches the executor; the executor runs the tool against the workspace; the verifier inspects the resulting artifact, not just the prose summary; and the loop either advances to the next decision, branches into structured repair, or escalates to a human. The dotted arrows are the diagnostic channels — typed errors, repair hints, observability — that distinguish a debuggable agent from a black box.

What three production agent stacks teach us

The three cards below summarize the reliability ideas worth importing from each major stack. They are not product comparisons; the point is that very different teams converged on the same set of mechanisms.

OpenCode

OpenCode’s archived Go repository documented a terminal AI assistant with TUI, multiple providers, session management, tool integration, SQLite persistence, LSP integration, file-change tracking, auto-compaction, and MCP support. Its current docs emphasize specialized primary agents with per-agent permissions, built-in and custom tools, and MCP servers. The takeaway for VPA is that agent permissions and tool surface should be declarative, scoped to the agent role, and inspectable from a TUI or log.

Sources: repository, agents docs, tools docs.

Codex CLI and Claude Code

Official Codex and Claude Code materials stress local execution, sandboxing, approval modes, subagents, project-level instructions, MCP integration, and context compaction. The product lesson is that users accept autonomy only when they can inspect diffs, logs, permissions, and recovery state. Stripped of marketing, both products are bets on the same architectural claim: long-running agents have to be debuggable end-to-end, or trust erodes within hours.

Sources: Codex repo, Codex safety, Claude Code overview, Claude subagents.

LangGraph and MCP

LangGraph’s value proposition is durable stateful execution, streaming, persistence, and human-in-the-loop control. MCP’s value proposition is a common way to expose resources, prompts, and tools to model applications. Together they suggest a clean separation between orchestration state and tool-provider interfaces — the same separation VibeProteinAgent already enforces between its agent controller and its tool broker.

Sources: LangGraph overview, LangGraph persistence, MCP specification.

VPA takeaway

VibeProteinAgent already has most of the architectural surface it needs: an agent controller, a Planner IR with local validation, a tool broker, and a workspace schema that persists jobs, artifacts, and retries. What is still missing is not new infrastructure but the deliberate use of the existing infrastructure as a training and verification substrate. Every place the architecture diagram shows a labelled artifact should also be a place where labels and verifier scores get written.

Section 4

A light post-training recipe

The temptation, especially with 8× B200s available, is to start with reinforcement learning. The literature and budget arithmetic both point the other way. Post-training works best when it is staged, when each stage produces an artifact the next stage needs, and when the earliest stages do not involve training at all. This section lays out that staged plan and is explicit about which methods are realistic at small scale and which are not.

The five-stage progression

Each stage in the list below is gated by the artifact the previous stage produces. Skipping a stage does not save time; it produces fragile training data that you will throw away later.

Stage 1: no-training improvements. Tighten the tool schemas, expand error messages into structured repair hints, add plan-only validators that reject obviously broken plans before any GPU touches them, and write canonical workflow templates the planner can compose from. These are the cheapest interventions and produce the cleanest data for everything that follows.

Stage 2: trajectory collection. Run the strongest available planner against the now-cleaner harness, log every step, and let deterministic verifiers label trajectories automatically. Verified traces become SFT candidates; repaired failures become reflection candidates; unrecovered failures become evaluation tasks. Nothing is thrown away.

Stage 3: small SFT. Fine-tune a 7B–14B open model or LoRA adapter to emit valid Planner IR and structured repair responses. The training mix should include general instruction data, not just protein workflows, to preserve language ability. AgentTuning is the relevant blueprint.

Stage 4: preference optimization. Only after SFT is stable should preference pairs come in, and only for cases where the two traces share the same task, inputs, and tool catalog but differ in cost, recovery quality, or final score. DPO on noisy unmatched pairs is worse than no DPO at all.

Stage 5: small verifier models. Train classifiers or reward models for plan validity, tool-call validity, scientific evidence quality, and candidate QC. These verifiers serve two purposes: they filter trajectories at training time, and they re-rank candidates at inference time. Small verifiers often outperform a single monolithic preference model.

Data lifecycle

The diagram below shows how a single agent run becomes the input to all five stages. Read the top row as the synchronous data path: every agent run produces a trace, which is automatically verified, then labelled, then routed into one of the training sets. What to log: trajectory schema for limited budgets

Every agent run should write a single replayable record. The fields below are the minimum that the downstream stages will actually consume. The cost of logging is small; the cost of discovering, three months from now, that the trace store is missing a field that every preference pair needs is enormous.

The generic fields are: user goal, normalized task type, planner prompt version, tool schema version, selected tools, the Planner IR itself, compiler errors, repair attempts, the compiled workflow DAG, tool inputs, tool outputs, artifact hashes, runtime cost, error codes, summaries, verifier scores, the final decision, and any user or expert feedback. For protein workflows, add sequence length, target identifiers, structural confidence, score names and thresholds, sampling seed, database snapshot identifier, citation provenance, and a claim-type label that distinguishes computational from literature-supported from experimentally validated claims.

Labeling: what makes a trajectory "good"

A trajectory should be considered good — and therefore eligible for SFT — only when the following hold together: every tool call validated against its current schema; every executed job either completed or was followed by a correctly diagnosed and recovered repair; the final candidate or report passed the domain QC gate; and the trajectory could be replayed from the persisted state without external dependencies that have since changed. Any single failure breaks acceptance, but the trace is not discarded; failed traces are routed to the reflection and verifier datasets.

A trajectory should be considered bad — and used only as a negative example or evaluation task — when the planner invented a tool that does not exist, when a failure was silently swallowed without any repair attempt, when the final report claims an artifact that does not exist in the workspace, or when the candidate appears to pass QC only because the QC step itself was skipped. These categories should be enumerated explicitly in the labeling guide so that two annotators reach the same verdict.

Reflection data: when to keep it and when to throw it away

Reflection traces (the agent generating a verbal critique of its own previous attempt) are useful in proportion to whether the critique led to a verified recovery on the next attempt. A "diagnosis → repaired plan → successful execution" triple is gold for SFT. A "diagnosis → repaired plan → second failure" triple is useful only as a negative example or for verifier training. A "diagnosis → no retry attempted" trace is garbage and should be dropped, because it teaches the model to produce fluent post-hoc rationalization without consequence. The rule of thumb is that reflection without a downstream action is not training signal.

Tool schema and observation formatting for training-friendly agents

Tool schemas should be designed twice: once for humans reading the documentation and once for the model that will eventually be fine-tuned to emit calls against them. Practically, this means each tool field should have a stable name, a concise description that includes one positive and one negative example, an explicit enumeration of supported modes, a clear statement of which inputs are required versus optional, and a typed error catalog. Tool outputs should always include a machine-readable status, an artifact reference, a one-line human summary, and structured diagnostics for the failure case. Prose-only tool results are the single most common reason agents fail to recover from errors: the model literally cannot tell a success summary from a failure summary if both are written in similar English.

How to construct an evaluation set

The evaluation set has to be built before, not after, training begins. A useful first set has four parts: roughly twenty replayable end-to-end tasks covering the canonical workflows; ten adversarial tasks with deliberately missing or corrupted inputs; ten "negative" tasks for which the correct answer is to refuse or escalate; and a small literature-grounded QA set with ground-truth citation spans. Tasks should be held out by protein family and by workflow type, never by random row split, so that improvements transfer to genuinely new targets. Cost-aware metrics — GPU hours per accepted candidate, retries per success — should sit next to accuracy metrics from the start, because budget pressure is a permanent constraint.

Recommendation, not established fact

A practical first training target is a 7B–14B open model or LoRA adapter that emits valid VPA Planner IR for common workflows. Use strong hosted models to generate N traces per task, deterministic validators to filter invalid traces, and a small expert review budget for borderline scientific claims. This is a recommendation for VPA based on the surveyed literature, not a result established by any single cited paper.

VPA takeaway

The first three months should produce zero new model weights and one excellent trace store. If the trace store contains replayable, labelled, schema-valid trajectories with verifier scores, the SFT stage becomes a weekend job. If it does not, no amount of GPU time will compensate.

Section 5

Protein and scientific-agent lessons

Protein-domain agents are roughly two years behind general-domain coding agents in maturity, and that gap is wider than the paper count suggests. The existing systems demonstrate tool orchestration, domain retrieval, and hypothesis generation, but the evidence base is narrower than product users need. The dangerous mode is not that protein agents fail loudly — it is that they succeed fluently while being wrong about the biology.

An initial protein-domain benchmark

A first internal benchmark does not need to be ambitious; it needs to be honest. A reasonable initial composition is roughly forty tasks split across four categories. The first category contains binder design tasks against a small panel of well-characterized targets where success can be measured by structural confidence, interface metrics, and downstream foldability. The second category contains structure-prediction tasks with deliberately ambiguous inputs (missing chains, mismatched stoichiometry) where the correct behavior is to flag the ambiguity rather than guess. The third category contains literature-grounded QA where the agent must cite specific spans and the answer key marks both correct citations and common hallucinated references. The fourth category contains MD setup tasks with deliberately broken inputs (wrong protonation, missing residues) where the correct behavior is repair and explanation, not silent execution. Cost-aware scoring should be enabled from the first run, since GPU hours per accepted candidate is a metric the team will care about long before raw accuracy moves.

VPA takeaway

Protein-domain agent research is currently dominated by demonstration papers with narrow benchmarks. The advantage VPA can claim is not yet another tool integration; it is reproducibility, verification, and honest uncertainty handling. The shortest path to scientific credibility is a small, fully replayable benchmark that includes negative tasks and adversarial inputs from day one, paired with the labeling discipline described in Section 4.

Metrics dashboard

Metrics should be tracked at four levels and reviewed together, not in isolation, because optimizing any single level alone produces predictable regressions in the others. Planning metrics include selected-tool accuracy, missing-input detection rate, Planner IR schema pass rate, compiler pass rate, and mean repair attempts per run. Execution metrics include job success rate, retry count, cache hit rate, runtime distribution, GPU memory utilization, and the empirical distribution of tool failure classes. Scientific metrics include structure confidence distributions, QC pass rate, ranking stability under reseeding, evidence coverage for cited claims, and reproducibility of replayed runs. Product metrics include cost per accepted candidate, time to first useful plan, final report faithfulness against the evidence the agent actually collected, and human override rate.

Avoiding shallow-trace overfitting

The most common failure mode in agent post-training is to train only on successful short traces and discover after deployment that the model has lost any ability to handle hard, messy, or adversarial inputs. The discipline to prevent this is uncomfortable but mechanical. Include hard negatives, missing inputs, ambiguous target identifiers, unavailable tools, malformed structure files, failed simulations, and contradicted literature in every training run. Keep task families held out by protein family and workflow type, not by random row split. Prefer labels from execution and domain validators over labels from the model's own self-judgment. When synthetic traces are used, reject any trajectory that cannot be replayed cleanly in a fresh workspace. These rules are tedious in the short term and decisive in the long term.

Final VPA takeaway

The shortest path from the current codebase to a credible, training-augmented protein agent is not glamorous. It is: clean schemas, plan-only validators, an exporter, a small honest benchmark, and a structured trace store. Once those are in place, a single weekend of SFT will produce more durable improvement than three months of unguided RL. Build the substrate first; the models follow easily.
